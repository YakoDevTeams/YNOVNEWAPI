Documentation partenaire

Création d’une souscription

Cette page décrit l’endpoint de création de souscription et les données à lui transmettre.

Endpoint

Envoyez les informations du souscripteur, des assurés, des bénéficiaires et du contrat, avec les fichiers justificatifs obligatoires en multipart.

POST /api/v1/partners/souscriptions

Route partenaire authentifiée, limitée à 10 requêtes par minute.

Connexion partenaire et jeton Bearer

Connectez-vous avec votre compte partenaire. Le jeton retourné sera automatiquement ajouté au formulaire de test de souscription.

POST /api/v1/auth/login

Cette route de connexion reçoit du JSON (Content-Type: application/json).

Corps attendu :

{
  "login": "......@gmail.com",
  "password": "",
  "device_name": "Documentation"
}
Aucune connexion effectuée.

Authentification et en-têtes

Les requêtes de souscription nécessitent un jeton d’accès Bearer valide.

Authorization: Bearer <VOTRE_JETON>
Accept: application/json
Content-Type: multipart/form-data; boundary=<générée par le client>

Laissez le navigateur ou votre client HTTP générer automatiquement l’en-tête multipart et sa boundary. Ne définissez pas manuellement Content-Type lors de l’envoi des fichiers.

Le mot de passe est envoyé uniquement à l’endpoint de connexion et n’est pas conservé par cette page. Utilisez cette documentation exclusivement en HTTPS. Si le compte exige une vérification 2FA ou un changement de mot de passe, la connexion ne fournira pas encore de jeton utilisable.

Structure du payload

Propriété Type Contenu
adherentData Objet Informations personnelles du souscripteur principal.
assurerDatas Tableau Assurés. Chaque élément contient is_adherent, info et sante.
BeneficiaireDatas Tableau Bénéficiaires. Respectez exactement cette casse. is_adherent vaut oui ou non.
documentDatas Tableau Fichiers justificatifs à rattacher au contrat. Leur absence ou un échec de stockage ne bloque pas la création, mais les pièces restent nécessaires au traitement.
contratData Objet Informations commerciales, financières et de prise d’effet du contrat.

Modes de paiement

Code à transmettre Signification Informations requises dans contratData
VIR Virement bancaire. Les coordonnées bancaires sont obligatoires : code_banque, code_guichet, numero_compte et rib. numecompte_complet peut également être fourni si disponible.
EBANK Mobile money ou paiement électronique. Indiquez EBANK comme mode de paiement.
SOlde Prélèvement sur la solde d’un fonctionnaire. La référence MECANO ou le matricule est obligatoire dans autre_ref_prelev.
ADF Le partenaire encaisse la cotisation, puis reverse les fonds à Yako Africa. Indiquez ADF comme mode de paiement.

Code de périodicité

contratData.code_periodicite attend l’indice suivant :

CodePériodicité
MMensuelle
TTrimestrielle
AAnnuelle
SSemestrielle

Références produit et formule

Les valeurs de code_produit, libelle_produit et formule_produit_code seront communiquées ultérieurement selon la convention avec Yako Africa. N’inventez pas ces valeurs ; renseignez-les lorsque votre interlocuteur vous les aura fournies.

Cas présentés : le souscripteur Ali est l’assuré 1 et le bénéficiaire 1 (is_adherent: "oui"). Aminata est un autre assuré et un autre bénéficiaire (is_adherent: "non") : ses renseignements personnels complets sont fournis dans chaque section. Si le souscripteur n’est pas assuré ou bénéficiaire, ne l’ajoutez pas comme tel ; fournissez les renseignements des personnes réellement concernées.

À retenir : les données personnelles de l’adhérent sont transmises dans adherentData. Pour chaque assuré, les données de santé sont dans sante. Les identifiants partner_uuid, conseiller_uuid et agence_uuid ne doivent pas être envoyés par le partenaire : le serveur les déduit du compte authentifié. Le partenaire vient de users.partner_uuid, le conseiller est l’UUID de l’utilisateur connecté, et l’agence est son agence principale active. Un compte sans partenaire ou agence principale active ne peut pas créer de souscription.

L’exemple JSON présente les données métier. Pour l’appel réel avec les pièces jointes, le corps de la requête est envoyé en multipart/form-data ; la page de test convertit le JSON en champs multipart et ajoute les fichiers sélectionnés.

Pièces justificatives

Pour le traitement du contrat, la pièce d’identité doit être fournie en deux fichiers distincts : le recto et le verso. Envoyez-les dans documentDatas avec un libellé explicite pour chaque côté. Leur absence ou un échec de stockage n’empêche pas la création de la souscription ; la réponse le signale dans documentWarning. Les fichiers sont envoyés en binaire via multipart/form-data, pas encodés en base64 dans le JSON.

documentDatas[0][libelle] = "Pièce d’identité - recto"
documentDatas[0][file]    = fichier binaire du recto
documentDatas[1][libelle] = "Pièce d’identité - verso"
documentDatas[1][file]    = fichier binaire du verso

Extensions acceptées par le service : PDF, DOC/DOCX, XLS/XLSX, CSV, PPT/PPTX, JPG/JPEG, PNG, GIF, WEBP, ZIP, RAR et TXT. Dans les clients HTTP, les noms de champs doivent conserver la notation avec crochets ci-dessus.

Tester l’endpoint

Attention : une requête réussie crée réellement une souscription. Utilisez un environnement de test et un payload adapté. Les fichiers recto et verso sont facultatifs à la création, mais nécessaires au traitement du contrat.

Résultat

Aucune requête envoyée.

Transmettre le contrat à Yako Africa

Après la saisie et la création, le contrat doit être transmis à Yako Africa pour traitement. Reprenez l’UUID contratData.uuid_contrat de la réponse à la création, puis appelez cette route avec le même Bearer.

POST /api/v1/esouscription/transmettre-contrat/{uuid}

Remplacez {uuid} par l’UUID du contrat. Aucun corps JSON n’est requis. La réponse confirme la transmission et retourne le contrat mis à jour.

Créez d’abord le contrat pour récupérer son UUID.

Exemple cURL

curl --request POST \
  --url 'https://<HOTE_API>/api/v1/esouscription/transmettre-contrat/<UUID_DU_CONTRAT>' \
  --header 'Authorization: Bearer <VOTRE_JETON>' \
  --header 'Accept: application/json'

Exemple d’appel cURL

Les fichiers justificatifs imposent un envoi multipart. Représentez les objets et tableaux JSON avec des noms de champs PHP entre crochets, comme dans l’extrait ci-dessous ; ajoutez de la même façon les autres champs de votre payload. N’ajoutez pas vous-même l’en-tête Content-Type, cURL génère la boundary multipart.

curl --request POST \
  --url 'https://<HOTE_API>/api/v1/partners/souscriptions' \
  --header 'Authorization: Bearer <VOTRE_JETON>' \
  --header 'Accept: application/json' \
  --form 'adherentData[nom]=DIOP' \
  --form 'contratData[mode_paiement]=ADF' \
  --form 'contratData[code_periodicite]=M' \
  --form 'documentDatas[0][libelle]=Pièce d’identité - recto' \
  --form 'documentDatas[0][file]=@piece-recto.jpg' \
  --form 'documentDatas[1][libelle]=Pièce d’identité - verso' \
  --form 'documentDatas[1][file]=@piece-verso.jpg'

Réponse

La réponse contient le contrat créé et le résultat de l’enregistrement des documents. Si les fichiers sont absents ou si leur stockage échoue, documentStore est vide et documentWarning explique que la souscription a été créée sans pièces jointes.

{
  "success": true,
  "message": "Souscription créée avec succès",
  "code": 200,
  "contratData": {
    "uuid_contrat": "UUID_DU_CONTRAT"
  },
  "documentStore": [
    {"document": {"uuid_document": "UUID_DOC_RECTO", "libelle": "Pièce d’identité - recto"}},
    {"document": {"uuid_document": "UUID_DOC_VERSO", "libelle": "Pièce d’identité - verso"}}
  ],
  "documentWarning": null
}

documentStore contient le résultat d’enregistrement de chaque fichier transmis. Une erreur de stockage est journalisée et retournée sous forme de documentWarning, sans annuler la souscription. Les autres erreurs de création continuent, elles, à faire échouer la transaction.
